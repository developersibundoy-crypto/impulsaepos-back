## Preflight e idempotencia

### Transporte autenticado (corrección S1)

Producción exige `ssl: { rejectUnauthorized: true, verifyIdentity: true, minVersion: 'TLSv1.2' }`. En mysql2 instalado, `verifyIdentity` habilita la comprobación del nombre del certificado; `rejectUnauthorized` exige una cadena de confianza válida. El nombre autenticado es el DNS de conexión `srv1779.hstgr.io`, no el @@hostname SQL. Por defecto se utilizan las raíces de confianza de Node. Si el proveedor requiere una CA específica, declarar `DB_SSL_CA_FILE=<archivo PEM>` en el archivo de entorno explícito; la ruta relativa se resuelve respecto a ese archivo. Obtener la CA por un canal autenticado del proveedor. Un archivo ausente/inválido o certificado no confiable causa error; no existe fallback sin TLS y `DB_SSL=false` no deshabilita este control.

La API `migrate` exige los dos flags verdaderos en la configuración real, stream TLS cifrado y autorizado y certificado válido para el DNS fijo mediante `tls.checkServerIdentity`. Antes de identidad SQL, preflight, bloqueo o DDL ejecuta `SHOW SESSION STATUS LIKE 'Ssl_cipher'` y exige exactamente una fila con valor textual no vacío. Una mera configuración SSL o identidad SQL no basta. La excepción sin TLS queda autorizada explícitamente **solo para ensayo local** mediante el tercer argumento/`--rehearsal-db`, conservando las restricciones de nombre, base y peer loopback de R1. La excepción no se puede utilizar para producción.
